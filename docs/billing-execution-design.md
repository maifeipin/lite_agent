# 有界任务执行与账单流程

本次问题样本：2026-10-10，任务 0b0c66a1。Planner 使用 5,892 Token，拉取 Worker 使用 61,888 Token，分析 Worker 使用 149,072 Token；总计 216,852，超过 200,000 的任务额度，发送节点被跳过。

## 执行边界

通用 DAG 保留原有接口。`execute_result()` 提供独立的 `TaskResult`：执行状态、失败/跳过节点、用量和投递回执。`execute()` 仍返回字符串。失败 Worker 的已有工具结果和内容保留；失败依赖不启动发布节点。失败报告使用代码模板，IM 状态不交给模型压缩。

账单固定流程需要 `task_routing.billing_workflow.enabled=true`，仅匹配最新账单拉取和分析；显式其他收件人、删除、转账、标记操作等继续走通用 DAG。固定流程为：

1. 执行现有 `exec3m`、`validate3m` 拉取和解析命令，每个命令超时 180 秒。
2. 只读读取 `billing.statement_db_path`，未配置时使用 `billing.script_dir/statements.db`。
3. 以邮箱、银行、UID 关联交易；取最近指定账期，并显式补充各邮箱/银行最新历史账期。
4. 生成完整明细和确定性异常；模型仅接收有界交易样例、账单数据和规则检查结果。
5. 通常一次模型分析，只允许输出截断时补充一次；不开放模型工具循环。
6. 归档完整报告并使用配置投递。仅请求明确允许 HedgeDoc 时，允许从邮件失败回退到公开文档。

模型样例数量不会限制报告的完整明细。分析默认不超过两次调用、60,000 Token；单次输出默认不超过 2,048 Token。金额使用 Decimal，按币种及原始方向汇总。账单应还金额没有独立币种字段，因此不跨账单直接求和。数据库“未还款”不能证明现实逾期；同一银行/账期多记录可能是多卡，报告提示核实而不自动合并。

## 预算准入

`ExecutionBudget` 管理已消耗和已预约额度。Gateway 在每个请求开始前预约输入估算加输出上限，完成后结算真实用量。未知用量或请求失败按预约估算扣除，标记估算量，避免按免费请求处理。SDK 隐藏重试关闭，Runtime 可见的重试重新预约。

输入估算使用序列化请求的 UTF-8 字节数和 1.25 系数，包含工具 schema、调用参数和协议余量。这是保守的准入估算，不等同于精确 tokenizer 或货币费用。实际用量仍可能偏离，保留请求后的熔断。

通用 DAG 按所有待执行 Worker 分配剩余额度，而非仅当前批次。默认为最终汇总保留总 Token 的 10%，最多 8,000，及一个模型步骤；节点用量由 Gateway 实时结算，不再在批次结束后重复扣除。

## 证据与收敛

上游证据移出 system prompt，保留有限摘要和证据归档 ID。工具返回的可用原文在配置的 SQLite 输出归档中保存；模型上下文压缩不覆盖归档。工具入口既有 12,000 字符限制继续存在，归档不能恢复入口已截断的内容。

收益按整个模型轮次判断：一轮多个低收益工具不等于多轮。允许一次重新规划，再有两轮没有新增证据就无工具收尾。循环检测同时覆盖连续重复和交替循环。仅明确声明 `side_effect=False` 的成功查询在单次执行中复用；未知或有副作用工具不缓存。

## 投递语义

投递回执区分账单报告和执行报告。SMTP 接受表示“已提交”，不表示收件箱已收到。SMTP quit 失败不能使已接受的邮件再次通过别的账号发送。已提交的账单报告不会被 IM 长消息处理再次发出；结构化报告也不会额外付费调用摘要模型。

异常或历史数据缺口保留在报告中。部分邮箱拉取失败时，可以使用已有账单生成报告，但执行状态为 partial，不声称所有邮箱同步成功。Gmail 重新授权属于独立账号恢复工作。

## 验证

新增测试覆盖并发预算预约、串行后续额度、缺失用量扣除、失败证据保留、system 证据边界、交替循环、按轮收敛、币种与金额精度、只读数据库、完整明细投递、状态摘要不可覆盖和防止重复发送。

线上部署先备份原代码和活动配置，编译与数据库冒烟检查后重启；测试邮件使用现有配置收件人。所有者使用服务器实际 liteagent 账户。真实案例的报告和回执保存在 `workspace/billing-validation-20261010.md` 与同名 JSON，完整原文另有 SQLite 归档 ID。

## 实测发现的模型参数兼容问题

首轮真实案例已拉取并投递确定性明细，但两次模型调用都消耗满 2,048 个输出 Token 且正文为空。实际配置使用 DeepSeek driver，却传入 `extra_body.enable_thinking=false`。DeepSeek 的原生 Chat 开关是 `thinking.type=disabled`，见 [官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)。

OpenAIInvoker 现按明确的 provider 类型翻译 DeepSeek 的旧布尔开关，保持其他提供商的参数原样，显式 thinking 设置优先。示例配置也使用原生参数。模型耗尽输出而正文为空时，账单流程立即停止重复请求，不再为相同输入再支付一次费用。修正后的真实复测报告使用“修正版”邮件主题，取代首轮没有模型正文的报告。

## 最终真实复测结果

2026-10-10，vps1：报告涵盖 19 条账单、231 条交易，已核对全部交易表行数及正文。修正版分析调用 1 次，输入 4,393、输出 1,946，共 6,339 Token，finish_reason=stop；SMTP QQ 通道提交成功。包含首轮参数诊断，两轮合计 19,367 Token。

本次 exec3m 与 validate3m 均触发 180 秒超时；分析使用数据库现有账单，状态为 partial，仅失败项为部分邮箱拉取。报告明确不保证当前月账单完整，不能声称所有邮箱已更新。Gmail 授权刷新失败在首轮报告中已有记录，账号恢复仍需另行处理。
