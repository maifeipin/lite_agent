# 阶段二收敛执行与验收控制

本文件自第十二轮复核起替代“只按最新探针修补后再宣布整体完成”的交付方式。原三阶段目标、阶段二范围及权限限制不变。本文件不授权提交、推送、部署、重启或真实外发。

## 固定账本

机器可读清单为 `architecture/stage-2-closeout-ledger-20261016.json`，固定六个验收单元：

| ID | 单元 | 当前判定 |
|---|---|---|
| S2-C01 | 冻结交付、旧基线与哈希 | 已记录本轮快照，后续必须保持对应 |
| S2-C02 | 业务函数、配置和状态的迁移性质 | 批量审计生成，待逐项消歧 |
| S2-C03 | 已证实行为退化恢复 | 两项独立反例失败，阻塞 |
| S2-C04 | 唯一实现与既有关键行为 | 新服务已落地，待最终行为核对 |
| S2-C05 | 全量能力与符号追溯 | 待完整交叉核对 |
| S2-C06 | 最终门禁与阶段收口 | 依赖前五项完成 |

单元状态只用：待实施、待复核、已通过、阻塞；机器清单的初始细分状态映射到这四类。实施 AI 可提交“待复核”，最终“已通过”由 Codex 按证据确认。没有源码/验证证据不得按文件数或测试总数换算完成百分比。

## 实施规则

1. 先完成 S2-C02 差异分类再继续业务修改。以第八轮冻结工作区与此前已确认的 Codex 修补为依据；不能仅以 HEAD 为基线，因为它不含完整阶段二工作。
2. 每项差异归为：纯搬迁、必要调用/路径适配、已确认缺陷修补、未经说明的行为改变。注释、格式、类型提示与名字调整分开记录；不能把这些自动算算法重写，也不能把函数体相同自动算完整等价。
3. 未经说明的行为改变恢复原契约；必要的修补提供明确旧问题、行为差异及独立反例。暂停增加新业务抽象或以“更健壮”为由重写现有算法。无需一工具一服务，未要求增加服务文件数量。
4. 同一能力以旧函数/入口为追溯单位，多个入口允许归同一业务服务。删除、合并、重命名必须有去向说明；同一逻辑不能在 skills 与 feature 保留两份来维持旧 mock。
5. 实施按单元提交局部验收证据，先运行相关专项，不必每改一个文件都执行整套门禁。最终统一执行一次对应冻结源码的全量；失败后保留日志，按变更影响重跑。
6. 一项通过后只在其文件/依赖/契约发生变化时重新打开。新发现的问题必须关联上述单元并说明影响；确有新增范围先单列，不悄悄加入原验收。

## 交付冻结

实施方发出“可复核”后停止修改业务源码，交付 HEAD、完整工作区 patch、新文件和哈希。Codex 复核开始和结束核对哈希；有变化则标记具体受影响证据失效，不能用不同版本的源码和日志拼接通过结论。

Codex 如需小修，先记录变更，再重跑受影响验证并更新哈希。大范围行为恢复交由实施方依账本执行。不要在双方同时写业务源码的情况下进行最终验收。

## 本轮批量诊断的含义

从旧 33 个 skills Python 文件恢复原实现，扫描当前 feature 中 186 个顶层服务函数：57 个可在同名旧函数中匹配函数体和签名（忽略注释/docstring、装饰器、函数名与类型标注）；89 个存在同名差异，40 个未匹配或已重命名。

**这些是审计队列，不是 129 个缺陷，不是工作量比例，也不是 57 个已验收功能。** 合法委托和符号改名也会形成差异，模块常量、配置、路径与副作用还需单独核对。S2-C02 的完成条件是每项都有可审核分类，不要求每项新增测试。

## 执行方接续输出

交付六单元状态表，每项附：旧→新符号、差异类别、变更理由、用例/命令/结果、剩余问题与文件哈希。对 S2-C02 先给完整差异处置表，再整批恢复或验证；S2-C03 两个已知反例不能代表全部差异审计。C01-C05 完成后才提出阶段二整体收尾请求。

本轮只新增治理文档及诊断账本，没有修改业务源码。
